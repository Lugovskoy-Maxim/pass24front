# Сервисные заявки: MySQL и Bitrix24

Реализовано 5 октября 2026 года. Создание обращений арендаторами остаётся выключенным настройкой `tenantServiceRequestsEnabled`. Включение вебхука не меняет эту настройку. Pass и Android используют одну серверную очередь заявок, переписку и статусы.

## Ежедневная синхронизация MySQL

При обновлении существующего включённого подключения MySQL однократно устанавливаются автоматическая проверка и применение изменений в **03:00 по Москве**. Последующие изменения администратора, включая выключение проверки, сохраняются. Расписание доступно в «Администрирование → MySQL».

Проверка сравнивает фактические поля всех опубликованных/приватных офисов, метаданные, категории, доступность и финансовые сведения, а также строки настроенных архивных таблиц сервисных заявок. Ограничение на первые 500 офисов снято. Перестановка строк не считается изменением. Изменение метаданных без изменения даты WordPress обнаруживается.

Автоматическое применение обновляет уже связанные офисы в Pass. Назначения арендаторов, учётные данные и вручную настроенные услуги сохраняются. Новые несвязанные офисы и исчезнувшие записи требуют проверки в разделе связей; автоматического удаления офисов нет. Рабочие сервисные заявки остаются в MongoDB, запись заявок в архивный MySQL не возобновляется.

Дата успешной проверки и аренда задания хранятся в MongoDB: два экземпляра сервера не выполняют один запуск одновременно. После перезапуска пропущенная проверка выполняется при старте. Ошибка вызывает повтор через час. Неприменённые изменения сохраняются до успешного применения даже при неизменном отпечатке. Администратор видит время следующей проверки, результат применения и безопасное сообщение об ошибке.

## Подключение CRM

В серверном `.env`, используемом Docker Compose:

```dotenv
BITRIX_API_KEY=https://YOUR_PORTAL/rest/USER_ID/WEBHOOK_SECRET/
BITRIX_ENABLED=true
BITRIX_SERVICE_CATEGORY_ID=
```

Переменная содержит полный URL входящего вебхука с правами CRM. Ключ не отправляется в браузер/Android и не выводится в диагностике. Воронка сделок выбирается по имени «Сервис» без учёта регистра. При нескольких совпадениях задайте `BITRIX_SERVICE_CATEGORY_ID`. В воронке нужна хотя бы одна рабочая и одна успешная завершающая стадия. Для выбора сотрудников нужны права `user`, `user_basic` или `user_brief`, для уведомлений — `im`. Проверка подключения показывает доступность этих прав. Без прав на сотрудников автор ответа отображается как «Служба сервиса».

Администратор с правом `support.manage` видит подключение, кнопку «Проверить подключение» и ссылку на связанную карточку. Проверка подключения читает воронку и стадии, не создаёт тестовых заявок или комментариев.

## Клиент, компания и ответственный

Название сделки имеет формат **«Д-2/6-18 м², Тема заявки»**: сокращение названия БЦ «Добрынинский-2», номер офиса 6, площадь 18 м² из карточки офиса и тема заявки. Сокращение строится из первых букв названия БЦ с сохранением номера корпуса. Используется выбранный офис; если у старой заявки несколько офисов без выбранного, ссылки на них разделяются точкой с запятой. При отсутствии площади этот сегмент пропускается, при отсутствии БЦ используется «Офис 6», без офиса — только тема. Названия уже связанных сделок обновляются при очередном опросе CRM. В описании сохраняются номер заявки Pass, ФИО заявителя, доступные телефон/email, компания, офис и заказанная услуга. Контакт и компания также привязываются к полю «Клиент» сделки.

Существующий контакт ищется по телефону/email, компания — по точному названию. При неоднозначном совпадении интеграция показывает ошибку привязки и продолжает обновлять чат и статус. Существующие контактные данные, заметки и основной контакт CRM сохраняются. Новые записи создаются с постоянной привязкой к Pass; после неизвестного результата отправки повтор сначала ищет уже созданную запись. Связанные сервисные заявки получают клиентские сведения при очередном опросе CRM.

В «Пользователи → редактирование арендатора → Компания в Bitrix24» администратор с правом `admin.users` выбирает существующую компанию CRM через поиск. Связь сохраняется отдельной кнопкой и применяется к заявкам арендатора и его сотрудников, включая уже связанные заявки. Снятие связи не удаляет компанию/контакт из CRM и не очищает вручную заполненное поле клиента.

В «Сервисные заявки → Ответственный за новые заявки → Настроить» администратор с правами `support.manage` и `admin.settings` один раз выбирает действующего сотрудника Bitrix24. Настройка копируется в новую заявку при её создании; смена настройки влияет только на последующие заявки, включая случаи задержки отправки в CRM. В отдельной связанной заявке сотрудник с правом `support.manage` может заменить ответственного.

После назначения Pass отправляет сотруднику уведомление Bitrix24 со ссылкой на CRM-карточку. Уведомления создаются для новых назначений Pass, а не при обогащении старых заявок. Постоянный тег защищает запись уведомления от дублирования при повторной отправке. Ошибка прав или доставки показывается в карточке и не блокирует переписку/статусы; доставка повторяется при опросе CRM.

## Переписка и статусы

- Новая заявка Pass сохраняется вместе с первым сообщением и заданием отправки в одной транзакции. Затем создаётся сделка в «Сервис» с номером заявки, категорией, арендатором, офисами и заказанной услугой. Старые заявки подключаются при следующем ответе; массового переноса истории без действия нет.
- Сообщения Pass становятся комментариями CRM. Имя и роль автора сохраняются в тексте. Служебный маркер связывает комментарий с исходным сообщением и исключает повторный импорт.
- В чат Pass/Android приходят только комментарии CRM, начинающиеся с **`(ответ)`**, например `(ответ) Мастер прибудет к 12:00`. Регистр и оформление текста не влияют на распознавание; сама метка не показывается арендатору. Упоминание метки внутри заметки не публикует комментарий. Ответ может содержать только вложение при наличии метки. Изменения и удаления опубликованных ответов обновляют соответствующее сообщение, сохраняя его место в истории.
- Для арендаторов автор ответа CRM обозначается [должностью сотрудника `WORK_POSITION` Bitrix24](https://apidocs.bitrix24.com/api-reference/user/user-get.html), а не его ФИО. Если должность не заполнена или вебхук не имеет доступа к ней, показывается «Служба сервиса». В админке сохраняется имя сотрудника. При опросе обновляются также подписи прежних ответов; это не создаёт новых сообщений и непрочитанных отметок. Сведения об авторе кешируются на пять минут, после чего изменения должности подхватываются автоматически.
- Остальные комментарии и их вложения остаются в Bitrix24. Удаление метки или обнаружение старого импортированного комментария без неё заменяет текст в Pass на «Комментарий скрыт в CRM», убирает вложения и закрывает доступ к их скачиванию по прежней ссылке. Добавление метки публикует комментарий, повторное добавление восстанавливает то же сообщение. Исходящие сообщения Pass не импортируются обратно.
- Активная стадия (`P`/process) → «В работе»; успешная (`S`/success) → «Завершён»; неуспешная (`F`/failure) → «Отменён». Повторное открытие CRM возвращает возможность ответа. Для связанной заявки ручное изменение статуса в Pass выключено.
- Получение изменений CRM выполняется опросом: каждая карточка планируется примерно раз в минуту. При большой очереди и задержках API обновления могут занимать больше времени. Входящий REST-вебхук является способом авторизации исходящих запросов Pass, а не подпиской на события CRM.

Входящие файлы скачиваются только с HTTPS-домена портала, максимум 10 файлов по 10 МБ, с существующей проверкой содержимого. Недоступное вложение отображается по имени и проверяется повторно. Правки исходных комментариев Pass в CRM не переписывают оригинальное сообщение Pass.

При сетевой ошибке заявка и сообщения остаются в Pass. Очередь повторяет доставку с увеличением задержки до часа. Если результат создания сделки/комментария неизвестен, интеграция сначала ищет уже созданный объект по привязке/маркеру. При отсутствии результата повторное создание блокируется и выводится сообщение о необходимости сверки: это предотвращает дубли после тайм-аута. Переход владения операциями в `paused`/`mstyle` останавливает CRM-работник.

## Проверка после обновления

Производственный workflow запускает `backend/scripts/check-integrations.cjs` внутри контейнера. Диагностика только читает настройки и метаданные CRM; выводит `INTEGRATIONS_CHECK` с готовностью подключения, воронкой/семантикой стадий, расписанием MySQL, числом ожидающих заданий и текущим флагом доступности обращений. Секреты и личная переписка не выводятся.

Локальные интеграционные проверки используют MongoDB replica set и подменённый Bitrix24: транзакции, повторы, неоднозначный результат доставки, входящие/исходящие вложения, статусы, запрет создания арендаторам, ежедневный запуск и восстановление после сбоя. В production проверка подключения не создаёт CRM-карточек.
