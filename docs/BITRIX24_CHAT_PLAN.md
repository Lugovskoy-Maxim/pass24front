# План интеграции чатов заявок Pass с Битрикс24

Дата: 3 октября 2026 года.

**Статус: отложено по указанию пользователя «битрик пока пропусти». В текущие изменения сайта и приложения интеграция не входит.**

Пользователь выбрал полноценный чат: администратор отвечает из Битрикс24, а арендатор получает сообщение в своей заявке на сайте Pass и в Android. Интеграция охватывает создание переписки, дальнейшие сообщения, обновления и связь с CRM.

Документ подготовлен по проверке локального кода и официальной документации REST API. Подключение к конкретному порталу и отправка сообщений в Битрикс24 на этом этапе не выполнялись.

## 1. Подход к подключению

Использовать локальное серверное приложение Битрикс24 с OAuth и пользовательским коннектором «Pass — заявки арендаторов» для «Открытых линий». Входящие POST-события приложения принимает сервер Pass.

Методы коннектора требуют авторизации приложения; входящий REST-вебхук для них не подходит. Это прямо указано в [официальном примере интеграции чата](https://apidocs.bitrix24.ru/tutorials/openlines/example-connector).

CRM-методы создания и обновления карточек поддерживают вызов через входящий вебхук. В выбранном варианте целесообразно использовать авторизацию того же приложения, добавив нужные права CRM; отдельный вебхук остаётся возможным инструментом для независимых CRM-операций.

## 2. Что получает пользователь

1. Арендатор создаёт заявку в Pass и выбирает офис, если их несколько.
2. В Битрикс24 появляется связанная переписка: номер заявки, компания, офис, категория и тема.
3. Оператор отвечает в открытой линии Битрикс24. Ответ появляется в той же заявке на сайте и в Android; используется существующий механизм уведомлений Pass.
4. Следующее сообщение арендатора приходит в ту же переписку Битрикс24.
5. В CRM хранится связанная карточка обращения с офисом, типом офиса, услугой, ценой при наличии, состоянием заявки и ссылками на переписку.
6. В Pass сохраняется история с автором и источником ответа. Администратор видит состояние доставки и может открыть соответствующий объект Битрикс24.
7. Ответ администратора из существующего интерфейса Pass также синхронизируется с сохранением авторства; способ отправки от сотрудника Битрикс24 проверить в минимальном прототипе.
8. Существующие заявки подключать по выбранному правилу и переносить историю однократно, сохраняя связи сообщений. Подключение старого чата не создаёт повторную CRM-карточку.

## 3. Проверенные методы и события

| Задача | API / событие | Применение |
| --- | --- | --- |
| Регистрация канала | `imconnector.register` | Создать коннектор приложения и страницу его настройки |
| Подключение к линии | `imconnector.activate`, `imconnector.connector.data.set` | Активировать выбранную открытую линию и сохранить параметры |
| Сообщение арендатора | `imconnector.send.messages` | Передать сообщение и внешние идентификаторы пользователя, заявки и сообщения |
| Ответ оператора | `OnImConnectorMessageAdd` | Принять ответ из Битрикс24 и сохранить в чат Pass |
| Подтверждение доставки | `imconnector.send.status.delivery` | Подтвердить успешную запись ответа в Pass |
| Изменение переданного сообщения | `imconnector.update.messages` | Обновить ранее отправленное сообщение по сохранённым ID |
| Изменение ответа оператора | `OnImConnectorMessageUpdate` | Обновить соответствующее сообщение Pass с сохранением истории |
| Удаление сообщения | `imconnector.delete.messages`, `OnImConnectorMessageDelete` | Согласованно обработать удаление, если такая функция разрешена |
| Название переписки | `imconnector.chat.name.set` | Обновить номер офиса, тему или подпись категории |
| Жизненный цикл диалога | `OnImConnectorDialogStart`, `OnImConnectorDialogFinish` | Учитывать создание и завершение сессии открытой линии |
| Карточка заявки CRM | `crm.item.add`, `crm.item.update` | Создать и обновлять выбранный вид CRM-объекта |

Источники: [обзор коннекторов](https://apidocs.bitrix24.ru/api-reference/imopenlines/imconnector/index.html), [ответ оператора](https://apidocs.bitrix24.ru/api-reference/imopenlines/imconnector/events/on-im-connector-message-add.html), [обновление ответа](https://apidocs.bitrix24.ru/api-reference/imopenlines/imconnector/events/on-im-connector-message-update.html), [обновление сообщения](https://apidocs.bitrix24.ru/api-reference/imopenlines/imconnector/imconnector-update-messages.html), [создание CRM-объекта](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-add.html), [обновление CRM-объекта](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-update.html).

## 4. Отдельный чат для каждой заявки и связь с CRM

Связь должна включать:

- ID заявки Pass, выбранного офиса, компании и арендатора;
- ID установки приложения и портала, коннектора и открытой линии;
- внешний `chat.id`, внутренний ID чата Битрикс24 и ID текущей сессии;
- тип и ID карточки CRM;
- пары идентификаторов сообщений Pass ↔ Битрикс24, направление доставки и последнюю подтверждённую версию.

Предлагаемая граница переписки — одна заявка Pass. Простая передача разных `chat.id` недостаточна: при `CHAT_GROUP=false` коннектор группирует чаты по `user.id`. Режим `CHAT_GROUP=true` группирует по `chat.id`, но отключает CRM-трекер входящих сообщений и влияет на стандартную автоматическую связь с CRM. Эти особенности описаны в [imconnector.register](https://apidocs.bitrix24.ru/api-reference/imopenlines/imconnector/imconnector-register.html).

До основной реализации провести проверку на тестовом портале:

1. Создать две заявки одного реального арендатора и подтвердить, что сообщения не смешиваются.
2. Проверить режим группировки по заявке с сохранением реального автора сообщения.
3. Создать либо подобрать CRM-карточку обращения и связанный контакт/компанию. Тип карточки — сделка либо смарт-процесс «Заявки арендаторов» — выбрать по возможностям портала.
4. Сохранить двусторонние ссылки и ID между карточкой и чатом. Проверить доступную штатную связь с CRM на данном портале; автоматическую привязку в режиме группировки по заявкам заранее не предполагать.
5. Если штатное отображение чата внутри выбранной CRM-карточки требует дополнительной встройки, включить её в реализацию. Переход из CRM в полноценный чат Битрикс24 должен оставаться доступным.

Цветовые метки категорий в интерфейсе Pass сохраняются. В Битрикс24 категория передаётся в название и поля карточки; возможность такой же цветной метки в штатном заголовке Битрикс24 отдельно проверяется на портале.

## 5. Передача сообщений и вложений

1. Исходящее сообщение сначала сохраняется в MongoDB вместе с заданием доставки. После отправки сохраняются полученные ID Битрикс24 и подтверждённое состояние.
2. Входящий ответ Битрикс24 проверяется, сохраняется в существующую переписку Pass и получает устойчивый внешний ID. Подтверждение доставки отправляется после успешного сохранения, согласно [OnImConnectorMessageAdd](https://apidocs.bitrix24.ru/api-reference/imopenlines/imconnector/events/on-im-connector-message-add.html).
3. Повтор события или повторный вызов API обрабатывается по сохранённой связи сообщений. Ответ, пришедший из Битрикс24, не отправляется обратно как новое сообщение арендатора.
   При таймауте с неизвестным результатом создания объекта или отправки сообщения предусмотреть сверку и состояние «Требует проверки», чтобы слепой повтор не создавал дубликаты.
4. Сохраняются реальный автор, источник, время, направление и версия сообщения. Системные уведомления и внутренние заметки оператора обрабатываются отдельно от ответа арендатору.
5. Обмен вложениями выполняется сервером через проверенный формат API. Для исходящих файлов подготовить ограниченный доступ для скачивания Битрикс24; входящие сохранять с существующей проверкой формата и размера Pass.
6. Редактирование сообщений в Pass сейчас не подтверждено как готовая функция. Для обмена изменениями добавить серверную поддержку версий и разрешённые действия интерфейса; удаление сохраняет отметку и журнал действия.

## 6. Обновление заявки и CRM

1. Согласовать соответствие состояний заявки Pass и стадий выбранного CRM-объекта: новая, в работе, ожидание, завершена и остальные реально используемые состояния.
2. При изменении темы, офиса, ответственного, статуса или заказа услуги обновлять связанные поля CRM. Цена и условия берутся из вручную заполненного прайса и сохранённого заказа.
3. Для каждого синхронизируемого поля определить владельца данных или правило конфликта, чтобы встречные события не перезаписывали более новое изменение.
4. Событие закрытия сессии учитывать отдельно от выполнения заявки. Оно сообщает о завершении диалога, а не подтверждает оказание услуги: [OnImConnectorDialogFinish](https://apidocs.bitrix24.ru/api-reference/imopenlines/imconnector/events/on-im-connector-dialog-finish.html).
5. Для повторного обращения по той же заявке сохранять связь с перепиской и учитывать новую сессию. Новый заказ или новая заявка получают отдельную связь.
6. Обновления из CRM принимать через события приложения. Подписка `event.bind` требует авторизации приложения; входящий вебхук сам по себе не обеспечивает обратные события: [обзор событий](https://apidocs.bitrix24.ru/api-reference/events/index.html).

## 7. Надёжность и доступ

1. Хранить доставку сообщений в отдельной очереди MongoDB с повторами, задержками, ограничением числа попыток, порядком сообщений заявки и журналом ошибок.
2. В текущем коде есть очередь внешних операций и платёжный worker, который выбирает задания без фильтра по типу. Интеграции Битрикс24 нужен отдельный обработчик/очередь либо явное разделение типов до совместного использования; иначе платёжный worker будет брать чужие задания.
3. Проверять не только HTTP-ответ, но и успех каждого сообщения внутри результата API. Сбой портала сохраняет сообщение Pass и задачу доставки.
4. Хранить OAuth-токены на сервере в защищённом виде и автоматически обновлять их. Проверять портал, установку приложения и токен события; адрес REST не брать из непроверенного входящего события.
5. Ограничить доступ операторов соответствующими линиями/БЦ и правилами CRM. Категория, офис и клиентские данные берутся из проверенных связей заявки.
6. Квитанция «доставлено» означает, что сообщение принято сервером Pass. Чтение арендатором учитывать отдельно.

## 8. Этапы реализации

| Этап | Результат |
| --- | --- |
| 1. Проверка портала | Доступность локальных приложений, REST, открытых линий, вид CRM-карточки и режим отдельных заявок подтверждены |
| 2. Приложение и коннектор | Установка, OAuth, выбранная линия, обработчик событий и настройки подключения работают |
| 3. Минимальный двусторонний обмен | Новая заявка и ответ оператора проходят между Pass и Битрикс24 без смешивания заявок |
| 4. CRM и обновления | Карточка обращения, поля офиса/категории, статусы и переходы между карточкой и чатом связаны |
| 5. Полная переписка | Вложения, обновления сообщений, завершение и повторное обращение сохраняют историю |
| 6. Проверка сбоев и выпуск | Повторы, недоступность портала, обновление токенов и ограничения доступа проверены; подключение включается по БЦ/линии |

## 9. Что потребуется при подключении

- Адрес портала и его тип: облачный или коробочный; фактически доступные приложения, REST и открытые линии.
- Установка локального серверного приложения и настройка его прав: `imopenlines`, необходимые методы `im`, `crm` и доступ к файлам по выбранному способу обмена.
- Выбранная открытая линия, очередь операторов и правила доступа по БЦ.
- Вид CRM-карточки, её поля и соответствие стадий статусам Pass.
- Публичные HTTPS-обработчики установки, настроек и событий приложения.

Секреты приложения и токены вводятся в защищённых серверных настройках. Их наличие необходимо для фактического подключения; данный план не требует передачи секретов в переписку.
