# Перенос операций Mstyle в Pass

Исходные версии: Pass 7160e94, Mstyle production-current 721297d / GitHub-копия 0331032.
Не включать режим `pass`, пока импорт и сверка не завершены. Режим `mstyle` оставляет прод на прежнем владельце; `paused` закрывает изменение операций.

## Матрица совместимости

| Сценарий | Сохраняемый контракт | Проверка |
| --- | --- | --- |
| Витрина | booking-rooms, booking-room-slots, booking-hold | Цена, услуги, интервалы, резидент и GuestParty |
| Полная оплата часами | awaiting_confirmation + paid | Однократное списание; неполная анкета допустима |
| Наличные / счёт | awaiting_payment → paid → confirmed | Нельзя подтверждать неоплаченное |
| Карта / QR + часы | hold → результат ЮKassa | Часы списываются после успешной оплаты, повтор webhook безопасен |
| Кабинет | account-bookings, details, extend, transfer, repeat, cancel-request | Прежние HTML и формы, цифровые ID |
| Отмена | cancelled | Возврат только невозвращённых часов, без фиктивного возврата денег |
| Счёт | invoice.pdf, отправка | Старый шаблон, данные/номер/состояние из Pass |
| Поддержка | account-support/tickets, reply, read, attachments | Темы, статусы, переписка, закрытые вложения до 10 МБ |
| Баланс | Общий resource_profile_id, периоды, квота | История не проигрывается заново при импорте |
| Счётчики | Общие для команды | Просмотр не снимает задачу; ожидание клиента не считается |

Этапы: доменные сервисы → серверные адаптеры → админка → импорт с dry-run → проверки → GitHub Actions + FTP → пауза и переключение.
После включения записи в Pass откат к старой MySQL без переноса новых операций запрещён.

## Локальная реализация и режим выпуска

Прод не переключён. В исходном состоянии обе стороны используют владельца `mstyle`.
Новые административные экраны показывают режим подготовки, финансовый worker не работает.
Push в main Pass автоматически запускает Deploy production; до отдельной команды на выпуск push запрещён.

Реализованы Mongo-сервисы операций, изолированные GridFS-вложения, очередь внешних действий,
идемпотентные команды с контролем версии и общей транзакционной границей. Конфликты бронирования
проверяются после захвата блокировок помещения/дня. Обновление fence владельца в каждой
транзакции исключает одновременно продолжающуюся запись после переключения режима.

Mstyle: прежние шаблоны и JS не изменяются. Серверные адаптеры сохраняют числовые ID, параметры
и ответы маршрутов витрины и ЛК. После переключения старые административные страницы ведут
в Pass; старые операции записи и задания часов/оплат блокируются. Каталог остаётся редактируемым.
Заголовок проекции `person-v1` сохранён для R-01.

## Подготовка будущего выпуска

1. Сохранить резервные копии MongoDB, MySQL, файлов вложений, конфигурации и текущие Git SHA.
2. Настроить `MSTYLE_OPERATIONS_SITE_URL=https://mstyle.ru` и отдельный случайный
   `MSTYLE_OPERATIONS_SHARED_SECRET` длиной не менее 32 символов в закрытом окружении Pass.
   На стороне WordPress тот же секрет задаётся константой `TF_MSTYLE_OPERATIONS_SHARED_SECRET`
   в закрытой конфигурации. Эти значения не передаются браузеру и не коммитятся.
3. Добавить backend OAuth-клиенту три права: `mstyle.operations.public`,
   `mstyle.operations.resident`, `mstyle.operations.system`. Существующие права сохранить.
   В режиме `mstyle` новые права не являются обязательными для старых пользовательских сценариев.
4. Проверить Mongo replica set, стабильный `MSTYLE_PII_KEY`, SMTP и nginx body limit 20M.
   JSON-загрузка файла разрешает 15 MiB на соответствующих маршрутах; сам файл не более 10 MiB.
5. Выпустить Pass штатным GitHub Actions, Mstyle — FTP, оставляя владельца `mstyle`.
   Миграционные скрипты находятся в backend/scripts и включены в образ backend.
   PHP-экспортёр временно помещается в закрытый каталог сервера, вне web root.
6. Включить закрытые серверные endpoints каталога и рендера: подпись HMAC, timestamp,
   одноразовый nonce. Проверить их связность. Рендер PDF не изменяет финансовое состояние.

## Экспорт, импорт и сверка

Экспортёр требует WP-CLI и загруженную тему. Каталог назначения должен существовать вне web root.
Экспорт содержит персональные данные и платёжную конфигурацию; хранить закрыто, не в Git.
Никакие перечисленные ниже команды на проде в рамках локальной реализации не выполнялись.

```sh
wp eval-file /private/export-mstyle-operations.php /private/operations-preliminary
# На стороне Pass, с окружением нужной БД и ключом шифрования:
node scripts/operations-migrate.cjs check /private/operations-preliminary/manifest.json
node scripts/operations-migrate.cjs import /private/operations-preliminary/manifest.json --write
node scripts/operations-migrate.cjs verify /private/operations-preliminary/manifest.json
```

Для запуска вне контейнера сначала собрать backend и загрузить закрытый env, например
`node --env-file=.env scripts/operations-migrate.cjs ...`. В контейнер каталог экспорта
нужно отдельно передать закрытым томом или через docker cp. Содержимое manifests не выводить
в общие логи. `--report /private/report.json` сохраняет отчёт без персональных данных.

Импорт заменяет записи по уникальным исходным ключам и может повторяться до открытия Pass.
Остатки копируются как состояние: журнал никогда не проигрывается повторно. Нумераторы
поднимаются до максимального исторического ID. Старые снимки преобразуются в зашифрованные
снимки Pass, только явно гостевые записи становятся GuestParty. Сведения об исходных
записях дополнительно сохраняются в зашифрованном архиве.

Отчёт должен содержать `issues: []`, а verify — `ok: true`, `differences: []`.
Сверяются числовые поля, суммы, связи, исходный архив, снимки и SHA-256 каждого файла.
Неоднозначные авторы/профили, отсутствующие снимки, вложения, владельцы часов и оплата
без подтверждающей истории останавливают открытие записи. Сначала исправить связи по
документально подтверждённым исходным ID и повторить экспорт; телефон/email не служат
основанием назначения владельца. Исходный архив никогда не публикуется в API.

## Короткая пауза и открытие записи

1. На Mstyle установить `tf_mstyle_operations_owner=paused` (или одноимённую константу
   `TF_MSTYLE_OPERATIONS_OWNER`). Константа имеет приоритет над опцией; не оставлять противоречие.
   Проверить отказ изменяющих запросов, продолжение чтения витрины/ЛК и остановку старых
   фоновых обработчиков этих доменов. Дождаться уже начавшихся старых запросов и заданий
   доставки/привязки снимков, проверив их очередь. Работники других интеграционных доменов
   остаются в работе. Переключение флага само по себе не останавливает уже запущенный PHP-процесс.
2. Выполнить `node scripts/operations-migrate.cjs pause --write` в Pass.
   Webhook старого URL в этот период только ставится в устойчивую очередь Pass.
3. Сделать новый финальный экспорт в отдельный каталог при `owner_mode=paused`.
   Повторить check, import и verify. Сопоставить отчёт также с независимыми суммами исходной БД.
4. Выполнить `node scripts/operations-migrate.cjs open /private/final/manifest.json --write`.
   Команда требует паузу, импорт именно этого digest, replica set и сверку без расхождений.
5. Установить владельца Mstyle в `pass`. Проверить оформление, оплату, отмену, общие часы,
   ответы и файлы в ЛК, обе роли администратора и счётчики у двух сотрудников.
6. Сохранить архивные таблицы MySQL. Все новые операции записываются только в Pass.

До открытия: `rollback-before-open --write` возвращает режим Pass в `mstyle`, затем отдельно
вернуть флаг Mstyle. После первого открытия CLI запрещает повторный импорт и простой возврат
к старой базе. При проблеме ставить обе стороны на паузу и исправлять с сохранением новых данных.
После аварийного завершения импорта не снимать `migration_lock` автоматически: сначала убедиться,
что исходный процесс завершён, сохранить состояние и снять только соответствующий export_id.

## Внешние операции

Очередь Mongo переживает перезапуск, имеет lease и отложенные повторные попытки. Webhook
не считается доказательством оплаты: сервер отдельно запрашивает платёж у ЮKassa, сверяет ID,
валюту и сумму. Смешанная оплата списывает часы только после полного подтверждения оплаты.
Для неоднозначного ответа создания сохраняется зашифрованное намерение платежа, которое
позволяет восстановить связь по проверенному уведомлению провайдера.
Повтор создания после 23 часов запрещён и требует сверки: срок идемпотентности ЮKassa —
[24 часа](https://yookassa.ru/developers/using-api/interaction-format).
Полученная после отмены оплата не восстанавливает отменённую бронь и требует решения администратора.
Отмена не запускает денежный возврат. SMTP-доставка имеет стабильный Message-ID, но SMTP
не гарантирует отсутствие повторного письма при разрыве соединения после принятия сообщения.

## Приёмка перед реальным переключением

Автотесты используют отдельный Mongo replica set и тестовые данные; рабочая база не затрагивается.
Проверка экранов выполняется с изолированным API, на ширинах 1440 и 390, в обеих темах.
Это не заменяет финальную сверку реальных данных и проверку платёжного магазина после выпуска.
Нужно проверить реальную конфигурацию каталога, SMTP, YooKassa, итоговые исторические связи,
набор выдаваемых OAuth scopes и частную доступность GridFS-файлов через Pass/Mstyle.


## Доплаты, реквизиты и исторические владельцы

При продлении сохраняются уже применённые цены и услуги; доплата рассчитывается только за
добавленное время по текущему каталогу. Поле кабинета `writeoff_min` для переноса/продления
означает дополнительные часы, а не замену всего предыдущего списания. Уменьшение времени
возвращает фактически списанные часы; автоматического денежного возврата нет.

Гостевая заявка администратора требует ФИО и телефон. При выставлении счёта недостающие
реквизиты запрашиваются отдельной формой и сохраняются в зашифрованном снимке документа.
Автор, GuestParty и исходный снимок заявки не меняются. Для резидента реквизиты берутся
из актуально заполненного профиля; обычная заявка по-прежнему допускает неполную анкету.
Счёт сохраняет сведения о помещении и времени на момент выпуска. Очередь отправки привязана
к конкретному номеру счёта и выбранному получателю, даже если позже бронь изменится.

Карточка и история часов администратора используют владельца, закреплённого в бронировании.
Последующее изменение связей профилей не переносит старое списание/возврат на новый баланс.


## Результаты локальных проверок, 22.09.2026

- Backend: 31 набор тестов, 422 проверки прошли; 1 ранее отключённый набор / 4 проверки пропущены.
  Из них 21 интеграционный сценарий новых операций работает на отдельном Mongo replica set.
- Сборки NestJS и Next.js проходят. Полный AppModule запускается в изолированном окружении;
  проверены JWT-защита, административные счётчики и маршруты обращений.
- PHP: синтаксис всех 14 изменённых/новых файлов темы и экспортёра корректен.
  Проверки адаптеров — 20; Pass-клиента — 960; публичных контрактов — 204 + 114;
  обращений — 19; неполной анкеты — 10; исторического владельца часов — 33.
- Браузер: списки, карточки и форма реквизитов гостя на ширинах 1440/390, обе темы;
  ошибок JavaScript и общего горизонтального переполнения нет; счётчик сохраняется при 503.
- Старый тест live-interface-baseline имеет 7 расхождений из 365 как до, так и после изменений;
  полученные хеши совпадают между исходной и изменённой версией. Эталон не обновлялся.
- ESLint новых backend-файлов не имеет ошибок; остаются предупреждения unsafe-argument при
  передаче Mongo-документов. Next.js сообщает прежние предупреждения React Hooks в других экранах.

Push, Actions, FTP, импорт реальных данных и переключение владельца не выполнялись.
Матрица выше описывает реализованные сценарии; реальная сквозная приёмка на конфигурации
прода и финальная сверка экспорта относятся к будущему выпуску, а не к этим локальным тестам.
